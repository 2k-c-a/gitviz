# 프로젝트 구조 유지 규칙 (영구)

제정일: 2026-10-30 · 대상: 이 저장소에서 일하는 모든 사람과 AI 에이전트 · 기준 구조: [최종 디렉터리 구조](FINAL_DIRECTORY_TREE.md)(4차에서 적용 완료)

함께 읽기: [최종 아키텍처](FINAL_ARCHITECTURE.md) · [환경 아키텍처](ENVIRONMENT_ARCHITECTURE.md) · [데이터 저장 정책](../deployment/DATA_STORAGE_POLICY.md) · [빌드와 릴리스](../deployment/BUILD_AND_RELEASE.md)

이 문서는 구조를 **유지**하는 규칙이다. 구조를 바꾸는 일은 별도의 아키텍처 개선 작업이며 이 규칙으로 허용되지 않는다. 기능 추가는 필요한 최소한의 파일만 바꾼다.

## 1. 작업 시작 전 (필수)

1. `git status`로 현재 상태를 확인한다. 이미 있던 변경은 내 것이 아니다. 임의로 커밋·되돌리기를 하지 않는다.
2. 위 네 문서가 **실제로 존재하는지** 확인하고 읽는다. 하나라도 없으면 구조를 추측해 작업하지 말고 사용자에게 보고한다.
3. 대상 파일·폴더를 검색해 같은 역할의 기존 코드가 있는지 확인한다.
4. 변경 범위(수정할 파일 목록)를 먼저 정한다.

## 2. 어디에 무엇을 두는가

| 종류 | 위치 | 비고 |
|---|---|---|
| 서버 코드 | `app/` (`workspace` 제외), `migrations/` | HTTP 라우터는 `app/api/`. `app/routers/`는 없다 |
| 데스크톱 에이전트 소스 | `app/workspace/` | 서버 DB·네트워크 모듈을 import하지 않는다 |
| Electron 셸 | `desktop/` | 비즈니스 계산 금지 |
| 웹 UI 자원 | `frontend/` | |
| 프로세스 간 계약(JSON Schema) | `contracts/` | 공유 계약의 유일한 위치 |
| 에이전트 동결 입력 | `packaging/agent/` | spec, 잠금된 빌드 의존성 |
| 테스트 | `tests/{server,frontend,workspace}`, `desktop/tests` | 이 밖에 테스트 파일을 두지 않는다 |
| 빌드·검증·운영·VM 도구 | `tools/{build,validation,ops,vm}` (`ops/legacy`는 일회성) | 제품 코드 금지 |
| 문서·보고서 | `docs/` (배포 관련은 `docs/deployment/`, 구조는 `docs/architecture/`) | 새 문서는 반드시 [문서 안내](../index.md)에서 연결 |
| 모든 빌드 산출물 | `build-output/` (Git 제외) | 설치 파일 후보는 `build-output/release-candidates/` |
| 검증 증거·VM 상태 | `.validation/` (Git 제외) | 증거는 커밋하지 않는다 |
| 사용자 데이터·로그 | 사용자 PC의 데이터 경로([데이터 저장 정책](../deployment/DATA_STORAGE_POLICY.md)) | 설치 폴더·저장소 폴더 금지 |
| 임시 작업 파일 | 세션 임시 영역(에이전트는 지정된 scratchpad), 사람은 `%TEMP%` | 저장소 소스 폴더 금지 |

여기에 없는 용도의 위치가 필요하면 만들지 말고 §6 절차로 보고한다.

## 3. 디렉터리 보호

- 정의된 구조를 임의로 바꾸지 않는다. 같은 역할의 폴더를 중복 만들지 않는다(`backend/`, `shared/`, `infrastructure/`, `config/`, `scripts/`, `build/`, `dist/`는 의도적으로 만들지 않는다 — 근거는 [결정 기록](ARCHITECTURE_DECISIONS.md)).
- **프로젝트 루트에 새 파일을 만들지 않는다.** 루트에 있는 파일은 [최종 디렉터리 구조](FINAL_DIRECTORY_TREE.md)에 적힌 것뿐이다.
- 기존 모듈에 기능을 넣을 수 있으면 새 모듈을 만들지 않는다.
- 소스 폴더에 임시 파일·테스트 결과·로그·DB를 저장하지 않는다.
- 개발용과 운영용 파일을 섞지 않는다.

## 4. 파일 생성 절차

1. 목적을 한 문장으로 정한다. 2. 같은 기능의 기존 파일을 검색한다. 3. §2 표에서 위치를 정한다. 4. 이름과 역할이 일치하는지 확인한다. 5. 만든다. 6. import·참조·문서 링크를 확인한다.

이름은 역할을 드러낸다. 금지: `new_file.py`, `test_new.py`, `temp_final.py`, `helper2.py`, `final_version.py`, `test123.py` 같은 의미 없는 이름, 버전·날짜 접미사로 복제본을 만드는 이름(`foo_v2.py`, `foo_old.py`).

## 5. 폴더 생성 제한

다음 이유로는 폴더를 만들지 않는다: 파일 몇 개를 나누려고, 기존 폴더와 역할이 겹침, 일회성 결과물 보관, 임시 테스트 결과, 기존 구조에 넣을 수 있음.

## 6. 구조 변경이 필요할 때 (사전 보고 후 승인)

다음을 보고하고 **승인을 받은 뒤** 진행한다: 폴더 생성 목적 · 기존 구조로 해결할 수 없는 이유 · 예상 파일 구성 · 다른 모듈과의 관계 · 최종 배포(패키지)에 미치는 영향. 승인된 변경은 같은 작업에서 [최종 디렉터리 구조](FINAL_DIRECTORY_TREE.md)와 [이동 이력](MIGRATION_HISTORY.md)에 반영한다.

## 7. 승인 없이 하지 않는 작업

기존 파일·폴더의 삭제, 이동, 이름 변경 · 공통 모듈 통합 · 설정 파일 위치 변경 · 데이터베이스 파일 이동 · 사용자 데이터 삭제 · **Git 이력을 바꾸는 명령(`reset --hard`, `clean`, 강제 push)** · 커밋, push, 의존성 설치, 서명, 배포, 외부 서비스·AI 호출. `.env`는 열어 보지 않는다.

쓰이지 않는 것처럼 보여도 바로 지우지 않는다. 사용처를 검색하고(코드·CI·compose·문서·문자열 참조) **삭제 후보 보고서**를 만들어 승인받는다.

## 8. 환경 보호

개발 DB를 운영에 쓰지 않는다 · 운영 사용자 데이터를 개발 시험에 쓰지 않는다 · 개발용 환경 변수를 패키지에 넣지 않는다 · 사용자 데이터를 설치 폴더에 두지 않는다 · 빌드 산출물과 소스를 섞지 않는다 · 배포에 필요한 파일만 패키징한다. 환경 분리 구조 변경은 사전 승인 대상이다. 통합 시험용 DB·Redis는 일회용 컨테이너를 쓰고 개발용 컨테이너(`gitviz-db-1`, `gitviz-redis-1`)와 호스트의 실제 사용자 데이터는 건드리지 않는다.

## 9. 코드 수정

기존 구조·스타일을 따른다 · 필요한 최소 파일만 바꾼다 · 기존 공통 모듈을 먼저 쓴다 · 중복 구현 금지 · 불필요한 의존성 추가·설치 금지(추가가 필요하면 먼저 보고) · API·DB 계약(`contracts/`, `migrations/`, OpenAPI)은 임의로 바꾸지 않는다 · 영향이 있는 수정은 테스트한다.

## 10. 작업 완료 전 검증

- 변경·신규 파일 목록을 확인한다(`git status`). §2 위치를 벗어난 파일, 루트의 새 파일, 새 폴더가 없어야 한다.
- 테스트와 정적 분석을 실행한다. 명령은 [개발 환경 설정](../development/DEVELOPMENT_SETUP.md)과 `.github/workflows`를 따른다. 테스트가 소스를 읽는 경로는 컴파일 산출물(`desktop/dist`)이므로 수정 후 다시 빌드한다.
- import·경로 참조를 확인한다. 문서를 건드렸으면 `python -B -I docs/audit/check_documents.py`를 통과시킨다.
- 내가 만든 임시 파일을 정리한다. 다른 사람·에이전트가 만든 파일, 사용자 데이터는 지우지 않는다.

## 11. 완료 보고 형식

작업 목적 · 수정한 파일 · 새로 만든 파일 · 삭제한 파일 · 폴더 구조 변경 여부 · 의존성 변경 여부 · 테스트 결과 · 빌드 영향 · 남은 문제. 바꾸지 않은 항목도 필요하면 "변경 없음"으로 적는다. 하지 않은 시험은 PASS로 쓰지 않고 NOT TESTED로 쓴다.

## 12. 원칙

구조를 임의로 개선하지 않는다. 기존 아키텍처를 기준으로 하고, 기능 추가는 필요한 최소 파일만 바꾼다. 폴더 구조 변경은 별도 아키텍처 개선 작업이다. 확장하되 질서를 훼손하지 않는다.

## 부록. 현재 알려진 구조 이탈 (규칙 위반으로 만든 것이 아니라 정리 대기 상태, 승인 전에는 손대지 않는다)

저장소 루트의 `reports/`, `test-react/`, `storage/`(Git 추적·무시 모두 아님 또는 런타임 폴더), 추적되지 않은 `Claude outputs/`·`outputs/`(무시됨) — 최종 구조 문서에 없는 항목이다. 용도 확인 후 삭제·이동 여부는 삭제 후보 보고서로 따로 승인받는다. 알려진 코드 이탈은 [알려진 문제](../deployment/KNOWN_ISSUES.md) K-08·K-09에 있다.
