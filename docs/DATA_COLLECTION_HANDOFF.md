# 데이터 수집 담당 전달 사항

## 지표 후보 정책 적용 작업 지시 — 2026-10-03

이번 지표 수정에서 `app/collectors/`와 수집 워커는 수정하지 않았다. 아래는 데이터 수집 담당 작업이다.

### 대규모 변경 판정 근거 보존

- 대상: Git commit/file collectors, GitHub PR collectors. 기준은 `changed_file_count >= max(15,ceil(0.1*N))`이며 등호를 포함한다.
- N은 가능하면 해당 커밋/PR의 기준 트리 파일 수를 수집한다. 어떤 트리(parent/base/head)를 사용할지 합의하고 저장해 재현 가능하게 한다. merge commit의 diff 기준도 함께 기록한다.
- 현재 백엔드는 목표 SHA 파일 수를 대용으로 계산한다. 과거 N을 수집한 뒤 백엔드 담당과 필드·migration·계산 버전 변경을 연결한다. 수집 플래그만 바꿔도 현재 스냅샷 정책은 바뀌지 않는다.
- changed_file_count는 API/Git의 전체 변경 파일 수로 저장한다. 상세 페이지 부분 수집 건수로 대체하지 않는다. 생성 파일·lockfile 제외 정책을 추가한다면 분모와 제외 규칙도 버전 관리한다.
- 완료 기준: N=20일 때 변경 2개는 포함, 15개는 제외. N=151일 때 15개 포함·16개 제외. 동일 SHA 재수집 시 원시 데이터와 판정 근거 동일.

### PR 상세 수집 완전성

- PR별 파일 목록·연결 커밋·리뷰의 페이지네이션 완료 여부와 실패 이유를 기록한다. 인증 없음, 권한 부족, 한도 대기, 일부 페이지 실패를 구분한다.
- 현재 `pr_file_coverage`는 파일 상세가 하나 이상 있는 PR 비율에 불과하다. 상세 1/100 파일만 있어도 포함되므로 완전성 지표로 사용하지 않는다.
- 누락 상세만 재시도하고 저장은 중복 없이 수행한다. samplemod의 병합 PR 9개를 독립 조회와 대조하거나 동등한 작은 전용 저장소에서 검증한다.
- 완료 기준: 전체 페이지 성공이면 실제 PR 파일 목록과 일치. 중간 페이지 실패 시 partial 상태·실패 이유 보존. 재시도 후 누락 복구, 기존 행 중복 없음.

### 고정 기간과 기여자 식별

- 수집 커서와 분석 기간은 분리한다. 기본 분석은 180일이지만 raw의 과거 이력은 삭제하지 않는다. 사용자가 다른 구간을 지정하면 해당 구간의 수집 가능 여부를 확인한다.
- refactor 분류로 기여 기록을 초기화하지 않는다. 미식별 contributor는 임의로 같은 사람으로 합치지 않는다.
- 버그 수정 라벨은 기존 규칙을 유지하되 표본 PR/이슈를 사람이 확인하고 분류 오류를 기록한다. confidence 0.95를 실측 정확도라고 보고하지 않는다.

전달 산출물: 대상 저장소·기준 SHA·수집 범위·전체/수집 상세 수·실패 페이지·재시도 결과가 담긴 검증 기록. 새 컬럼은 Alembic migration과 함께 제공한다.

기준: 2026-10-02, `05a58db` 검토 후 백엔드 개선 작업.

## 우선 검증

| 우선순위 | 과제 | 위치 | 완료 기준 |
| --- | --- | --- | --- |
| 높음 | 작은 저장소 신규 수집 → 새 커밋 추가 → 재수집 | `app/collectors/git/*`, `app/tasks/analyze_repository.py` 수집 단계 | 새 커밋 반영, SHA 중복 없음, 기본 브랜치 커밋 수와 기준 SHA 파일 수 일치 |
| 높음 | 비공개 저장소와 권한 회수 | `clone_manager.py`, GitHub collector | 요청자 개인 토큰으로만 수집. 권한 회수 후 수집/조회 거부. 토큰이 URL·Git 설정·예외 로그에 남지 않음 |
| 높음 | 동명 저장소 격리 | `storage/repos/<repository_id>`, `clone_manager.py` | 서로 다른 owner의 같은 이름 저장소가 다른 경로/DB 데이터로 유지됨. origin 불일치 시 중단 |
| 높음 | 기본 브랜치 변경과 force push | Git commit/file collectors | 기본 브랜치 변경 후 최신 HEAD/도달 가능한 SHA 반영. 오래된 커서보다 과거 날짜인 새 reachable 커밋의 누락 여부 확인 |
| 중간 | PR/커밋/파일 연결 범위 | GitHub PR collectors, `pr_commits`, `pull_request_files` | 스냅샷의 PR 연결 건수와 독립 GitHub 표본 대조. 공동 수정 관계가 실제 파일 변경에 근거함 |
| 중간 | 과거 구간 수집 완전성 | 증분 커서와 API 페이지네이션 | 특정 분석 구간에 빠진 PR/리뷰/릴리스가 있는지 확인. 미수집 범위를 기록하고 수집 완료로 오인하지 않게 함 |
| 중간 | 기여자 식별 매핑 | `app/collectors/identity/resolver.py` | 이메일 alias 병합 중복 없음. 미식별·계정 미연결 건수를 독립 집계와 대조 |

큰 저장소 전체 재수집 전에 작은 전용 테스트 저장소에서 검증한다. 검증 기록에는 저장소, SHA, 실행 시각, 수집 구간, 기대값/실측값, API 한도를 기록한다.

## 백엔드에서 이미 개선한 계약

- 15분 초과 pending, 6시간 초과 running, 한도 재개 시각 120초 초과는 시간상 복구 후보다. 실제 교체는 수집 워커와 같은 PostgreSQL advisory lock을 획득할 때만 허용한다.
- 교체된 job은 `cancelled`이며 지연 도착한 메시지는 실행하지 않는다. 이 때문에 `app/tasks/analyze_repository.py`의 **작업 시작 전 terminal 상태 검사만** 보완했다. 커밋/PR/파일 수집 알고리즘은 유지했다.
- 잠금 키 `1735289201, repository_id`는 API 재시작과 워커 양쪽의 계약이다. 워커 잠금을 변경할 때 `app/services/job_lifecycle.py`와 함께 변경해야 한다.
- 스키마는 Alembic head `f3a4b5c6d7e8`로 관리한다. 새로운 컬럼/테이블은 수동 ALTER 스크립트만 추가하지 말고 migration도 함께 작성한다.
- 운영 수집·재분석·OAuth 실연동은 이번 백엔드 테스트에 포함되지 않았다. 실제 GitHub 연동 검증은 이 담당 영역에서 추가 확인해야 한다.

## 이후 개선

증분 수집은 timestamp 커서만으로 과거 날짜의 새 커밋을 놓칠 수 있으므로 Git 도달 가능한 SHA와 DB의 수집 SHA를 비교하는 방식의 비용/정확도를 평가한다. 실패한 API 페이지의 재시도와 수집 범위 추적을 도입하고, 성능 변경 전후에 API 호출 수·소요 시간·누락 건수를 비교한다.

## 실연동 검증 추가 결과 — 2026-10-03

- samplemod: 커밋 29·파일 18·변경 42, 병합 PR 9. Git 이력과 분석 조회는 정상이나 인증이 없어 PR 파일 상세는 0/9다.

- **소규모 필터:** 현재 10% 변경 비율은 파일 3개인 저장소의 커밋 6개를 모두 대형 변경으로 처리한다. 최소 변경 파일 수 조건과 비율 조건을 어떻게 조합할지 정책을 정하고, 작은/큰 저장소 양쪽에서 제외 건수와 결합도 영향을 비교한다.
- 세션 재연결 후 작업 완료 상태가 저장되지 않던 문제는 백엔드에서 실제 재현 후 수정했다. 수집 알고리즘은 유지했다.
