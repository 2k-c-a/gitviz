# 분석 타당성 검증 계획

이 문서는 실험을 재현하기 위한 계획이며 정확도 검증 결과가 아니다.

## 평가 질문

관측된 상대 위험도·변경 기여 집중도·공동 변경 신호가 이후 변경/버그 수정과 어떤 관계가 있는지 평가한다. BF는 실제 퇴사 시 장애 확률로, Risk Score는 결함 확률로 해석하지 않는다.

## 고정해야 하는 입력

- 평가 기준일 T, 저장소의 GitHub numeric ID, 기준 SHA, formula_version과 파라미터를 기록한다.
- 관측 구간은 `[T-2년,T-3개월)`, 검증 구간은 `[T-3개월,T)`로 분리한다. 평가일 변경 시 모든 대상에 같은 규칙을 적용한다.
- T-3개월 이후의 커밋·PR·리뷰·릴리스 및 나중에 보정한 정보를 예측 입력에 섞지 않는다. 과거 identity mapping을 복원할 수 없으면 현재 mapping 사용이라는 한계를 명시한다.
- 관측 파일별 커밋 수·PR 연결·미식별 비율을 기록하고, 데이터가 충분한 그룹과 부족한 그룹을 나눠 보고한다.

## 정답과 파일 대응

검증 구간의 bugfix 규칙 분류는 약한 정답이다. '실제 결함'이라고 부르지 않는다. 표본 PR/이슈를 사람이 확인한 결과를 따로 기록해 규칙 오분류를 측정한다.
파일 대응은 정확한 path를 기본으로 한다. 이동/삭제 파일을 제외할지 Git rename으로 대응할지 실험 시작 전에 고정하고 각각의 누락 건수를 공개한다.

## 비교 기준과 지표

- 변경 빈도만 사용, churn만 사용, 무작위 선택을 기준으로 둔다.
- 상위 10%·20% 점검 파일의 이후 bugfix 포함 비율(precision), 이후 bugfix 파일 중 찾아낸 비율(recall), lift를 기준과 비교한다.
- 파일 수와 관측량을 함께 제시하고 저장소별 결과 및 저장소 단위 평균을 모두 보고한다. 대형 저장소 하나가 전체 결과를 지배하지 않게 한다.
- BF/결합도는 보조 설명 변수로 검증한다. 관측량이 적은 그룹의 높은 비율을 강한 근거로 해석하지 않는다.
- 재표집 시 저장소/시간 구조를 보존한다. 성능 차이가 관측 구간과 저장소 종류에 따라 유지되는지 확인한다.

## 결과물

고정된 스냅샷 ID 목록, 원본 검증 라벨, 파일 대응 표, 제외 이유, 실행 파라미터와 비교 결과를 저장한다. 성능이 기준보다 좋아도 적용 범위를 명시하고 결함 확률로의 변환은 별도 보정 검증 없이는 하지 않는다.

실제 검증용 라벨·GitHub 수집 범위가 준비되지 않았으므로 이번 작업에서 실험을 실행하거나 정확도 수치를 만들지는 않았다.
