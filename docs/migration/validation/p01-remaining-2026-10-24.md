## 결론과 승인 범위

사용자의 P01 잔여 검증 요청으로 기존 격리 환경과 설치된 도구를 사용했다. 신규 패키지 설치·업그레이드·서버 DB/서비스·P02 구현·배포는 수행하지 않았다. 저장 중단 결함 보완, 회귀, agent/앱 재빌드, 독립 VM 검증 패키지와 실행 절차를 포함한다.

현재 **P01 부분 구현**이다. 정의한 중단 경계22개와 실제 SQLite 용량 초과 검사는 통과했다. clean Windows VM 실행과 물리 파일시스템 ENOSPC는 **환경 제약으로 검증 불가/미실행**이다. 개발 PC에서 PATH를 제한한 성공을 clean VM 통과로 승격하지 않는다.

## 검증으로 보완한 코드

- [store.py](../../../app/workspace/store.py): SQLite backup을 `.pending`에 작성하고 integrity 검사·flush 후 최종 backup 이름으로 게시한다. 중단된 backup을 완료된 복원본처럼 표시하지 않는다. Windows fsync에는 쓰기 가능한 handle을 사용한다.
- [secrets.ts](../../../desktop/src/secrets.ts): DPAPI key 암호문을 임시 파일에 완성·flush한 뒤 exclusive hard-link로 게시한다. 동시 생성된 key를 덮어쓰지 않는다. 기존 SQLite/암호문이 있는데 key가 없으면 새 key를 생성하지 않는다.
- [dispatcher.py](../../../app/workspace/dispatcher.py): 암호화 확인 파일도 완성·flush 후 exclusive 게시한다. 암호문 손상은 RECOVERY_REQUIRED, 지원하지 않는 schema는 UNSUPPORTED_PROTOCOL로 분류한다.
- [agent.ts](../../../desktop/src/agent.ts), [상태 UI](../../../desktop/ui/status.js): 정규 복구 오류를 프로세스 종료 후에도 보존하고, 무조건 재시작하라는 안내 대신 저장 상태 확인/복구 안내를 표시한다.
- hard-link를 지원하지 않거나 권한이 없는 파일시스템에서는 게시를 차단한다. 표준 사용자·로컬 NTFS 시험 범위의 결과이며 다른 파일시스템 지원은 Q01 결정/검증 없이 주장하지 않는다.

public RPC·기존 HTTP·서버 schema·기존 AI 정책 변경은 없다. 사용자 프로젝트 파일을 대상으로 하지 않으며 생성한 시험 자료에만 손상/강제 종료를 적용했다. hard-link 게시와 임시 파일은 모두 동일 앱/시험 디렉터리에 한정한다.

## 강제 종료 경계와 판정

실제 Windows 프로세스를 경계에서 정지시킨 뒤 부모가 TerminateProcess로 종료하고, 제한 시간 내 종료·재열기·무결성을 확인했다. 제품에 시험용 환경변수나 kill hook을 넣지 않고 자식 fixture에서 실제 저장 함수/SQLite API를 감쌌다.

| 영역 | 실제 중단 지점 | 통과 조건 |
|---|---|---|
| SQLite12개 | root 확인, writer lock, DB open, backup open, backup 진행 중, backup copy 완료, backup 게시, WAL 설정, BEGIN, DDL 후, INSERT 후, COMMIT 후 | integrity_check=ok, 미커밋 schema 없음/commit 이후 schema_meta 존재, 완료 backup은 유효, 재기동 성공. backup 이전 원본 hash 보존 |
| key5개 | 임시 파일 open, 부분 write, sync 후, exclusive 게시 후, 임시 이름 제거 후 | 최종 key는 완성본 또는 부재, 재기동 성공, 게시된 key 바이트 불변, 동시 승자 key 덮어쓰기 없음 |
| 암호화 확인 파일5개 | open, 부분 write, sync 후, 게시 후, ready | 재기동 ready, 이미 게시된 암호문 바이트 불변, 불완전 staging을 최종 자료로 채택하지 않음 |

이22개는 P01의 정의된 durable 경계다. 전원 단절·모든 CPU 명령 사이 중단·후속 N03 patch 적용/journal 인수를 의미하지 않는다.

## 용량 부족과 손상

SQLite의 max_page_count=1을 실제 파일 DB에 적용해 엔진이 SQLITE_FULL(13)을 발생시키게 했다. fake 예외만 던지는 시험과 구분한다. transaction rollback, 원본/backup integrity, 한도 제거 후 재기동을 확인했다. 호스트 디스크를 채우지 않았다. 이는 SQLite 용량 한도 초과이며 Windows 볼륨의 실제 ERROR_DISK_FULL/ENOSPC를 재현한 것은 아니다.

실제 Electron·번들 agent·OS DPAPI를 사용해 key 소실, key 암호문 손상, 확인 암호문 손상을 시험했다. 각 실패에서 ready를 거부하고 원본 바이트를 보존한다. 정상 시험 자료를 복원한 뒤 재기동 성공도 확인했다. 복구 오류는 실제 renderer health 브리지까지 전달된다. 자동 key 재생성이나 사용자 파일 원복은 없다.
