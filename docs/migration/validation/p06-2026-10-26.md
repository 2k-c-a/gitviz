## 사용자 승인한 파일 게시 예외

생성한 임시 text 두 개에서 대상 handle을 FILE_SHARE_READ로 열어 외부 write/delete를 막은 상태의 FileRenameInfoEx 교체가 WinError32로 실패했으며 원본 bytes는 유지됐다. Win32 handle rename의 기준은 [Microsoft FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)다. 단일 교체를 위해 배타 handle을 닫는 틈을 만들지 않는다.

사용자는 F03의 파일별 단일 원자 교체 대신 **배타 handle 유지 → durable 암호화 journal → 원본을 임시 보존명으로 handle rename → 새 파일을 원래 이름에 덮어쓰기 없이 게시**하는 2단계 방식을 승인했다. 중간 종료 시 원래 경로가 일시적으로 없을 수 있으므로 recovery_required를 표시하고 명시 승인 후만 복구한다. 제3자가 원래 경로에 파일을 만들면 게시/복구는 덮어쓰지 않는다. 실제 구현·native/kill-point 증거로 입증하기 전 안전성 완료를 선언하지 않는다.

원본 bytes가 프로젝트 안의 임시 보존명으로 이동하는 단계가 있으며, 그 경로·identity·preimage/target hash를 journal에 묶고 암호화 backup도 먼저 보관한다. 임시 자료는 renderer가 임의로 지정하지 못한다. 최종 파일 ACL/일반 파일 identity·index와 source hash를 검사하고 거절/재요청/재시작 시 기존 승인을 재사용하지 않는다. 다중 파일 원자성·전원 손실 무손실 보증은 하지 않는다. 실제 사용자 프로젝트에는 검증 중 쓰지 않는다.
