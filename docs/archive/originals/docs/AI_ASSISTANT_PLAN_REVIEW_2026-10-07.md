## 판단

현재 GitViz를 확장하는 방향으로 적합하다. 수정 집중도를 실제 업무량이나 지식 보유 인원으로 단정하지 않고, 인수인계 준비는 사용자 입력으로 확인한다는 구분이 특히 좋다. AI의 역할도 수치 계산 대신 설명·질문·초안 작성으로 제한되어 있다.

개발 전에 우선 확정할 것은 **근거에 따라 어떤 판단을 허용할지**와 **준비 정보의 저장·수정 권한**이다. 10장의 최소 구현 범위는 팀 진단, 준비 관리, 행동 관리, 문서 편집을 모두 포함하므로 첫 시연 범위로는 크다.

## 현재 구현과의 연결

| 기획 요구 | 코드에서 확인한 상태 | 추가할 부분 |

이번 최신화에는 수집 누락 기록 및 재수집과 결과 저장 확인 후 완료 표시가 포함됐다. 그러나 작업의 `done`은 PR 수집이 모두 완전하다는 뜻이 아니다. 워커는 스냅샷 저장 후 `done`으로 끝나며 수집 품질은 별도 필드다. AI에는 작업 상태와 근거 완전성을 구분해서 전달해야 한다.

## 기획에 보완할 사항

### 1. 수정 집중도의 단위와 분모

기획의 “수정 20건 중 18건”은 파일을 변경한 서로 다른 커밋 수인지 명시한다. 현재 파일별 비중은 식별된 기여자의 변경 커밋 수를 분모로 사용한다. 미식별 커밋이 있으면 전체 수정 중 비율처럼 설명해서는 안 된다.

동일 커밋이 3개 파일을 변경할 때 파일별 건수를 합하면 3건이 된다. 폴더·기능 집계에서 이 합계를 전체 커밋 수와 섞지 않도록, `대상 묶음을 변경한 고유 커밋 수` 또는 `파일별 변경 관측 수 합계` 중 하나를 정하고 화면에도 표시한다. 전자를 사용하려면 별도 집계가 필요하다.

현재 관측 수 5 미만은 표본 부족으로 분류한다. 집중 판단의 비중 기준·최소 관측 수·미식별 비중 처리 규칙은 기획에 추가하고 코드와 같은 버전을 사용한다. 예시의 90%를 검증 없이 보편적인 판단 기준으로 채택하지 않는다.

### 2. 수집 품질에 따른 판단 제한

근거가 부족한 판단만 제한한다. PR 상세가 불완전해도 커밋 근거가 충분하면 수정 집중도를 설명할 수 있지만, 리뷰 참여가 없다고 단정할 수는 없다. 관측이 0건이면 “수정 활동 없음”보다 “선택한 범위에서 관측 자료 없음”으로 안내한다.

각 설명에 기간, 대상, 관측 수, 미식별 비중, 관련 수집 상태와 근거 식별자를 붙인다. 높은 상대 점검 우선순위는 장애 확률이나 인수인계 준비 부족의 증거로 사용하지 않는다. 준비 부족 판단은 사용자가 입력한 항목에 한정한다.

### 3. 준비 정보를 기록하는 대상과 의미

준비 항목을 저장소 전체에 하나만 둘지, 기능/폴더/파일 묶음마다 둘지 정한다. 첫 버전은 사용자가 이름을 붙인 **인계 대상 파일 묶음 하나**로 시작하는 것을 제안한다.

미확인·준비 필요·준비 완료를 항목별로 기록하고 작성자, 수정 시점, 버전을 남긴다. 인수 담당자, 인수자 실행 확인 등 항목별 완료 조건을 정의한다. 문서 링크가 있다는 사실만으로 내용의 충분함이나 접근 가능 여부를 확정하지 않는다. “사용자가 완료로 기록함”과 시스템이 검증한 사실을 구분한다.

스냅샷을 바꾸거나 파일 이름이 변경되면 기존 준비 정보가 그대로 적용되는지 확인하도록 표시한다. 새 분석을 실행했다고 사용자 입력을 덮어쓰지 않는다.

### 4. 팀 협업 권한

현재 GitHub 저장소 읽기 권한 확인은 준비 체크폼과 문서의 수정 권한을 정의하지 않는다. 공개 저장소는 익명 조회도 가능하므로 읽기 가능 사용자가 모두 팀 문서를 수정하도록 해서는 안 된다.

팀원·관리자 역할을 도입할지, 첫 버전은 작성자 개인 공간으로 제공할지 확정한다. 편집과 삭제는 로그인 및 지정된 수정 권한을 요구한다. 실제 팀 협업이 필요하면 첫 버전부터 팀 구성원과 역할을 정의한다. 개인 공간을 선택하면 팀 공유는 후속 범위라고 명시한다. 조회·생성·수정·내보내기마다 저장소 권한과 문서 권한을 확인한다.

### 5. 외부 AI에 전달할 자료

코드 원문을 제외해도 파일 경로, 사람 이름, 내부 문서 링크와 메모에는 비공개 정보가 있을 수 있다. 생성 전 전달 항목을 알려주고 비공개 저장소에 대한 팀의 사용 허용 기준을 정한다. 문서 링크는 첫 버전에서 저장·표시만 하고 자동으로 내용을 읽지 않는다.

메모, 파일명, 저장소 설명은 분석할 자료로 처리하며 AI 행동을 바꾸는 지시로 사용하지 않는다. 문서 속 지시로 다른 저장소 조회나 추가 자료 전송이 일어나지 않도록 한다. 로그에는 API 키나 원문 메모를 불필요하게 남기지 않는다.

### 6. 생성 결과 검증과 변경 이력

모델에는 근거 ID가 붙은 제한된 자료를 보내고, 결과는 설명·근거 ID·제안·확인 질문으로 구분된 형식으로 받는다. 수치는 서버가 검증하거나 검증된 값으로 표시하고, 존재하지 않는 파일·담당자·근거를 참조하는 결과는 표시 전에 거부한다. 자유 문장 전체의 사실성을 자동 보장한다고 약속하지 않는다.

AI 결과에는 스냅샷 ID·해시, 준비 정보 버전, 입력 범위, 모델/프롬프트 버전, 생성 시점을 기록한다. 같은 자료의 반복 요청은 기존 결과 재사용을 우선 고려한다. API 제한 시간과 재시도 횟수를 정하고 중복 생성 요청을 제어한다. AI 오류가 분석 조회를 막지 않게 한다.

생성 원본과 사용자 편집본을 분리한다. 재생성으로 편집본을 덮어쓰지 않으며, 준비 상태가 바뀌면 이전 결과에 “이전 준비 정보 기준”이라고 표시한다. AI 출력은 Markdown/HTML로 표시할 때 실행 가능한 내용을 차단한다.

## 추천 최소 구현 범위

첫 시연은 **한 저장소의 고정 스냅샷 → 선택한 파일 묶음 → 준비 체크폼 → 근거 포함 점검 결과와 인수인계 초안 → Markdown 내보내기**로 연결한다.

필수 범위는 대상 선택, 항목별 준비 상태 저장, 검증된 근거 표시, 점검/초안 생성, 초안 보완, 내보내기, 생성 실패 안내다. 초안 보완은 일반 텍스트 편집으로 시작할 수 있다.

전체 팀 자동 진단, 별도 행동 목록과 진행 관리, 팀원별 통합 대시보드, 일정 추천, 문서 링크 자동 읽기, 풍부한 문서 편집기는 후속으로 미룬다. 행동 제안 자체는 점검 결과 안에 포함한다. 이렇게 해도 기획의 핵심인 “집중된 수정 활동과 준비의 빈틈을 연결한다”는 시연이 가능하다.

## 검증 기준에 추가할 사례

1. 동일한 근거에서 수치·대상·근거 참조가 일치하고, 미입력 상태를 준비 부족으로 바꾸지 않는다.
2. 변경 1건/0건, 미식별 기여자, PR 리뷰 실패가 있을 때 각각 허용된 설명만 한다.
3. 준비 완료 사례에 근거 없는 문제를 추가하지 않는다. 점검 항목별 입력과 출력의 대응을 확인한다.
4. 비권한 사용자의 조회·생성·편집·내보내기를 차단한다. 공개 저장소 읽기 권한이 문서 수정 권한으로 확대되지 않는다.
5. 악의적인 메모, 존재하지 않는 파일/근거, 모델의 잘못된 수치, 실행 가능한 출력이 안전하게 처리된다.
6. 준비 정보 변경·재생성·동시 편집에서 이전 결과와 사용자 수정이 보존된다.
7. 생성 실패·지연·중복 클릭에도 분석 조회가 유지되고 요청 상태가 명확하다.
8. 동일한 인계 과제로 AI 사용 전후의 작성 시간, 누락된 필수 항목, 인수자의 실행 확인을 비교한다. 소규모 사용 평가임을 표시하고 생산성 개선을 일반화하지 않는다.

## 이번 작업의 확인 범위

지정 커밋으로 코드 최신화하고 기획 원본을 읽어 현재 코드와 비교했다. 원본 기획 파일은 변경하지 않았다. AI 기능 구현, 운영 DB 마이그레이션, 서버 재시작·배포, 실사용자의 AI API 호출은 수행하지 않았다.

코드 최신화 후 PR 상세 수집 판정 15개, 분석 계산 9개, 지표 정책 12개 테스트가 통과했다. 프론트 지표 표시 및 시각화 순수 모듈 검사도 통과했다. 스냅샷 회귀 검사는 일부 사례 통과 후 실행이 멈춰 중단했으므로 전체 통과로 보고하지 않는다. PostgreSQL 통합 검사와 새 마이그레이션 적용은 이번 작업에서 실행하지 않았다.
