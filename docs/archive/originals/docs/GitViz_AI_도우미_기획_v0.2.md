# GitViz AI 도우미 기획 v0.2

**개발 기록과 준비 정보를 연결하는 인수인계 점검 도우미**

- 작성일: 2026-10-07
- 문서 버전: v0.2 — 기획 초안 보완
- 현재 기능 확인 기준: GitViz `0ecbca7`
- 문서 성격: 개발 제안. AI·준비 정보 관리 기능의 구현 완료를 의미하지 않습니다.

## 1. 프로젝트 소개

GitViz는 GitHub 개발 기록에서 특정 사람에게 수정 활동이 집중된 파일을 찾고, 사용자가 입력한 인수인계 준비 정보와 연결해 먼저 확인할 대상과 준비 항목을 알려주는 서비스입니다.

AI는 분석 엔진이 계산한 근거를 쉬운 말로 설명하고, 개선 행동·확인 질문·인수인계 문서 초안을 제안합니다. 사용자는 사실관계와 제안을 검토하고 최종 문서를 보완합니다.

> “어떤 파일의 수정이 누구에게 집중돼 있고, 그 부분을 인계하려면 무엇을 더 준비해야 할까요?”

수정 기록은 관측된 개발 활동입니다. 실제 업무량, 과로, 개인의 능력, 코드를 이해하는 사람의 수를 의미하지 않습니다. 서비스는 사람의 성과 평가보다 인수인계 대상을 찾고 준비를 돕는 데 초점을 둡니다.

## 2. 해결하려는 문제

특정 기능을 한 사람이 계속 수정하면 담당자가 휴가를 가거나 팀을 떠날 때 다른 팀원이 확인할 파일과 질문을 찾는 데 시간이 걸립니다. 기억에 의존한 인수인계에서는 자주 수정한 부분, 함께 확인할 파일, 실행·확인 절차가 빠질 수 있습니다.

개발 이력만으로는 문서가 충분한지, 인수자가 실행해 봤는지 알 수 없습니다. GitViz는 수정 기록과 사용자가 입력한 준비 상태를 구분해 다루면서 두 정보를 연결합니다.

## 3. 대상 사용자와 서비스 질문

| 사용자 | 필요한 도움 |
|---|---|
| 팀장 | 수정 활동의 집중 현황을 확인하고 지식 공유·인수인계 대상을 선정합니다. |
| 인계자 | 인계할 파일을 고르고 준비 상태를 정리하며 문서 초안을 보완합니다. |
| 인수자 | 먼저 확인할 파일과 질문을 파악하고 실행 확인 결과를 남깁니다. |

| 질문 | 제공할 결과 |
|---|---|
| 어디에 수정이 집중돼 있나요? | 파일별 기여 비중, 관측 수, 분석 기간과 설명 |
| 인수인계에서 무엇이 빠졌나요? | 입력된 준비 필요 항목과 아직 확인되지 않은 항목 |
| 무엇부터 하면 되나요? | 근거에 따른 확인 순서, 개선 행동과 질문 |
| 문서를 어떻게 시작하나요? | 대상·근거·준비 상태를 반영한 편집 가능한 초안 |

첫 버전은 로그인한 작성자의 개인 작업 공간으로 제공합니다. 작성자는 팀원에게 확인한 내용을 기록하고 문서를 내보내 공유할 수 있습니다. 팀장·인계자·인수자가 같은 화면을 공동 편집하는 기능은 후속 범위입니다.

## 4. v0.2에서 정한 핵심 원칙

1. 수치와 판단 근거는 분석 엔진과 준비 정보에서 가져옵니다. AI가 새 수치를 계산하거나 없는 사실을 추가하지 않도록 결과를 검증합니다.
2. 작업 완료와 수집 완전성을 구분합니다. 결과가 저장됐어도 PR·리뷰 정보가 누락될 수 있습니다.
3. 준비 상태를 입력하지 않으면 ‘미확인’입니다. ‘준비 필요’로 바꾸지 않습니다.
4. 수정 집중도는 개발 기록의 분포입니다. 사람에 대한 평가나 실제 지식 인원의 추정으로 표현하지 않습니다.
5. AI 결과는 검토할 제안과 초안입니다. 담당자 배정, 일정, 최종 문서는 사용자가 결정합니다.
6. 생성 원본과 사용자 편집본을 구분하고, 재생성으로 편집본을 덮어쓰지 않습니다.

## 5. 인계 대상과 준비 정보

### 5.1 인계 대상 설정

사용자는 한 저장소의 저장된 분석 결과를 선택하고 인계할 파일 묶음에 이름을 붙입니다. 예를 들어 ‘로그인 기능 인계’라는 대상에 관련 파일 3개를 지정합니다.

필수 정보는 대상 이름, 저장소, 분석 스냅샷, 파일 목록입니다. 인계자·인수자 이름, 인계 목적, 기능 설명과 메모는 선택 입력입니다. 첫 버전의 이름 입력은 메모 성격이며 서비스 계정의 역할이나 권한을 부여하지 않습니다.

기능 이름은 사용자가 입력한 설명을 사용합니다. 파일명만 보고 기능을 확정하지 않습니다. 첫 버전은 파일별 근거를 제시하며, 파일별 비중을 평균 내어 기능 전체의 담당자 비중처럼 표시하지 않습니다.

### 5.2 준비 체크폼

준비 정보는 인계 대상 파일 묶음별로 저장합니다.

| 항목 | 입력 정보 | 사용자가 ‘준비 완료’로 기록할 조건 |
|---|---|---|
| 인수 담당자 | 이름 또는 담당자 메모 | 인수할 사람을 정하고 이름을 기록함 |
| 기능 설명 | 설명 또는 문서 링크 | 기능과 인계 범위에 대한 설명을 작성함 |
| 실행 방법 | 설명 또는 문서 링크 | 환경 준비와 실행 절차를 작성함 |
| 수정 후 확인 절차 | 설명 또는 문서 링크 | 수정 후 확인할 방법과 기대 결과를 작성함 |
| 공동 검토 | 수행 여부와 메모 | 관련 파일을 함께 검토하고 결과를 기록함 |
| 인수자 실행 확인 | 수행 여부와 확인 결과 | 인수자가 직접 실행한 결과와 남은 질문을 기록함 |

각 항목은 **미확인 / 준비 필요 / 준비 완료**로 저장합니다. 초기값은 미확인입니다. 미지정·미작성·미수행을 사용자가 명시하면 준비 필요로 기록합니다. 완료 조건에 필요한 정보가 없으면 입력을 보완하도록 안내합니다.

‘준비 완료’는 사용자가 완료로 기록했다는 뜻입니다. 시스템이 문서 내용의 충분함이나 실제 실행 성공을 검증했다는 뜻은 아닙니다. 링크는 저장·표시만 하며 자동으로 접속하거나 내용을 읽지 않습니다.

작성자, 수정 시점, 준비 정보 버전을 남깁니다. 분석 결과나 대상 파일을 변경하면 기존 입력은 보존하고 재확인이 필요하다고 표시합니다. 변경된 대상을 사용자가 확인하기 전에는 이전 준비 정보를 최신 대상에 대한 확인으로 취급하지 않습니다.

## 6. 핵심 기능

### 6.1 수정 집중 현황과 근거 설명

기존 분석 결과의 파일별 수정 횟수, 기여 비중, 관측 수를 표시하고 AI가 설명합니다. 기본 관측 기간은 기존 분석 정책의 180일이며, 실제 선택한 스냅샷의 기간을 따릅니다.

파일별 수정 건수는 **해당 파일을 변경한 서로 다른 커밋 수**입니다. 현재 기여 비중의 분모는 기여자가 식별된 변경 커밋 수입니다. 전체 관측 수와 미식별 수를 별도로 보여줍니다.

**가상의 출력 예시**

> 선택한 180일 동안 `src/login.ts`를 변경한 커밋은 22건입니다. 기여자가 식별된 20건 중 18건(90%)이 민수님에게 해당합니다. 2건은 기여자를 식별하지 못했습니다. 인계 대상을 정할 때 이 파일을 먼저 확인해 보세요.

첫 버전은 최대 기여 비중과 관측 수로 확인 후보를 정렬합니다. 특정 비율만으로 정상·위험을 판정하지 않습니다. 관측 수가 5건 미만이면 현재 분석 정책에 따라 ‘표본 부족’을 표시하고 일반적인 집중 판단을 보류합니다.

### 6.2 인수인계 준비 점검

AI는 수정 근거와 체크폼을 연결해 준비할 내용을 설명합니다. ‘준비 필요’와 ‘미확인’을 별도 목록으로 표시합니다.

**가상의 출력 예시**

> `src/login.ts`의 식별된 변경 기록에서는 민수님의 수정 비중이 높습니다. 입력된 준비 상태에서 인수 담당자는 ‘준비 필요’, 실행 방법은 ‘미확인’입니다. 인수 담당자를 정하고 실행 방법이 정리돼 있는지 확인해 보세요.

준비 항목이 모두 완료로 기록돼 있으면 그 사실을 표시합니다. AI가 문제를 추가로 만들어내거나 문서가 충분하다고 자동 보증하지 않습니다.

### 6.3 개선 행동과 확인 질문

| 확인된 상황 | 제안할 행동 |
|---|---|
| 특정 사람의 수정 비중이 높음 | 주요 파일을 다른 팀원과 함께 검토할 대상을 선정합니다. |
| 파일이 반복적으로 함께 변경됨 | 함께 확인할 파일과 검토 질문을 정리합니다. |
| 인수 담당자가 준비 필요로 기록됨 | 팀에서 담당자를 정하고 기록을 갱신합니다. |
| 실행·확인 절차가 준비 필요로 기록됨 | 절차를 작성하고 인수자가 확인합니다. |
| 준비 상태가 미확인임 | 기존 담당자에게 현재 상태를 질문합니다. |
| 인수자 실행 확인이 준비 필요로 기록됨 | 직접 실행하고 결과와 질문을 기록합니다. |

행동 제안은 점검 결과 안에 포함합니다. 첫 버전에는 별도의 할 일 관리, 일정 배정, 진행 상태 보드를 만들지 않습니다.

### 6.4 인수인계 문서 초안

선택한 대상의 점검 결과로 다음 내용을 가진 초안을 만듭니다.

1. 인계 목적, 담당자 메모와 대상 파일
2. 먼저 확인할 파일과 분석 근거
3. 함께 확인할 파일과 공동 변경 근거
4. 항목별 준비 상태와 미확인 내용
5. 담당자에게 확인할 질문
6. 인수인계 체크리스트
7. 분석 기간, 준비 정보 기준 시점과 생성 시점

초안은 일반 텍스트로 편집·저장하고 Markdown으로 내보냅니다. 코드 원문이나 실행 절차가 입력되지 않았다면 이를 작성한 것처럼 만들어내지 않고 확인 질문이나 빈 작성 항목으로 남깁니다.

## 7. 근거가 부족할 때의 동작

| 근거 상태 | 허용할 설명과 안내 |
|---|---|
| 변경 관측이 0건 | ‘선택한 범위에서 관측 자료 없음’. 수정이 없었다고 확정하지 않음 |
| 관측 수가 5건 미만 | 수치는 표시하되 ‘표본 부족’을 함께 표시하고 집중 판단 보류 |
| 기여자 미식별 기록 존재 | 식별된 기록 기준임을 명시하고 미식별 수·비중 표시 |
| PR 또는 리뷰 수집 불완전 | 리뷰 부재·협업 부족 판단 제한. 확보된 커밋 근거는 별도로 사용 |
| 공동 변경 근거 부족 | 관련 파일 추천을 보류하거나 근거 부족 표시 |
| 준비 상태 미입력 | 미확인으로 표시하고 확인 질문 제시 |

분석 작업의 완료 상태만으로 근거 사용 가능 여부를 정하지 않습니다. 근거 종류별 수집 상태를 확인합니다. 높은 점검 우선순위는 저장소 안에서의 상대적인 후보 순위이며 장애 확률이나 준비 부족의 증거로 사용하지 않습니다.

과거 공동 변경은 함께 검토할 근거입니다. 파일 사이에 실제 의존 관계가 있거나 변경 영향이 반드시 전파된다고 표현하지 않습니다.

## 8. 사용자 흐름과 화면

**로그인 → 저장소와 분석 결과 선택 → 인계 대상 파일 묶음 설정 → 수정 근거 확인 → 준비 상태 입력 → AI 점검·초안 생성 → 검토·편집·저장 → Markdown 내보내기**

| 화면 영역 | 표시 내용 | 주요 동작 |
|---|---|---|
| 인계 대상 | 이름, 파일 목록, 선택한 분석 기간 | 대상 설정·변경 |
| 수정 근거 | 파일별 기여 비중·관측 수·수집 부족 상태 | 상세 근거 보기 |
| 준비 체크폼 | 준비 필요·미확인·완료 항목과 수정 시점 | 입력·저장 |
| AI 점검 | 근거가 연결된 설명·개선 행동·질문 | 생성·재시도 |
| 인수인계 초안 | 생성 원본과 사용자 편집 내용 | 편집·저장·내보내기 |

‘Bus Factor’, ‘Ownership Entropy’, ‘Co-change’보다 ‘수정이 집중된 부분’, ‘함께 확인할 파일’ 같은 표현을 우선 사용합니다. 상세 근거에서 기술 지표의 의미를 볼 수 있게 합니다.

준비 정보가 바뀌면 이전 생성 결과에 ‘이전 준비 정보 기준’이라고 표시합니다. 분석 결과가 바뀌면 선택된 기준과 기존 문서 기준을 구분합니다. 자동 재생성이나 편집 내용 덮어쓰기는 하지 않습니다.

## 9. 역할과 구현 방식

| 구성 요소 | 역할 |
|---|---|
| 분석 엔진 | 기간·대상을 고정하고 수정 비중, 관측 수, 공동 변경 및 수집 품질을 계산 |
| 준비 정보 관리 | 항목별 상태·입력 내용·작성자·버전 저장 |
| 백엔드 | 권한 확인, 근거 구성, AI 요청, 결과 검증 및 저장 |
| AI | 제공된 근거를 설명하고 행동·질문·문서 초안 제안 |
| 사용자 | 사실 확인, 준비 상태 기록, 문서 보완과 최종 결정 |

**분석 스냅샷 + 준비 정보 버전 + 선택 대상 → 근거 묶음 구성 → AI 요청 → 결과 검증 → 점검·초안 저장 → 사용자 편집·내보내기**

### 9.1 저장할 정보

| 정보 | 주요 내용 |
|---|---|
| 인계 대상 | 작성자, 저장소, 이름, 파일 목록, 설명·담당자 메모 |
| 준비 정보 | 항목별 상태·내용, 수정자·시점, 버전, 대상 변경 재확인 상태 |
| 생성 결과 | 분석 스냅샷 ID·해시, 준비 정보 버전, 입력 대상, 모델·프롬프트 버전, 생성 시점, 요청 상태 |
| 문서 편집본 | 연결된 생성 원본, 편집 내용, 수정 시점·버전 |

동시 수정은 버전을 확인해 덮어쓰기를 막습니다. 충돌 시 최신 내용을 확인하고 다시 저장하도록 안내합니다.

### 9.2 AI 결과 검증

근거에는 식별자를 붙입니다. AI 결과는 설명, 근거 식별자, 행동 제안, 확인 질문을 구분한 형식으로 받습니다. 존재하지 않는 파일·담당자·근거 참조는 표시 전에 거부합니다.

수치 표시에는 서버의 검증된 값을 사용합니다. 모델이 본문에 수치를 반복하면 원본과 대조하고 불일치 결과는 저장된 정상 결과로 취급하지 않습니다. 자유 문장의 모든 사실성을 자동 보장한다고 약속하지 않으며, 질문과 사용자 검토를 함께 제공합니다.

### 9.3 실패·중복 요청 처리

AI 실패와 지연은 분석 결과 조회를 막지 않습니다. 생성 상태는 대기·진행·완료·실패로 구분하며 실패 시 기존 입력과 편집본을 보존합니다.

요청 제한 시간, 자동 재시도 최대 횟수, 대상·메모 입력 크기 제한은 서버에서 관리합니다. 동일한 스냅샷·준비 버전·대상·모델·프롬프트의 중복 요청은 진행 중 요청 또는 기존 결과를 재사용합니다. 명시적인 재생성은 새 원본을 만들고 기존 편집본을 유지합니다.

## 10. 권한과 외부 AI 전달 범위

첫 버전에서는 인계 대상·준비 정보·생성 결과·편집본을 작성자만 조회·생성·수정·삭제·내보낼 수 있습니다. 각 요청에서 로그인, 작성자 권한 및 현재 저장소 접근 권한을 확인합니다. 공개 저장소를 읽을 수 있다는 이유로 다른 사람의 준비 정보나 문서에 접근할 수는 없습니다.

GitHub 접근 권한이 사라지면 저장소에 연결된 문서의 조회·생성·편집·내보내기를 차단합니다. 계정 로그인과 담당자 이름 입력을 팀 협업 권한으로 해석하지 않습니다.

외부 AI에는 선택 범위의 분석 수치, 필요한 파일 경로, 준비 상태, 선택한 설명·메모를 전달합니다. 코드 원문은 전달하지 않습니다. 문서 링크는 AI 입력에서 제외하고 서비스의 준비 정보 및 내보낸 문서에만 포함합니다.

생성 전 전달할 항목과 서버에 설정된 AI 제공자를 알려줍니다. 비공개 저장소의 외부 AI 사용은 팀에서 허용한 저장소에 한정하며, 허용 기준이 정해지기 전에는 공개 저장소로 시연합니다.

API 주소·키·모델은 서버에서 설정하고 키는 브라우저로 보내지 않습니다. 메모·파일명·저장소 설명은 분석 자료이며 AI의 행동 지시가 아닙니다. 입력 속 지시로 다른 저장소 조회나 추가 전송이 일어나지 않도록 처리합니다. API 키와 불필요한 원문 메모는 로그에 남기지 않습니다. 출력 표시 시 실행 가능한 HTML·스크립트를 차단합니다.

## 11. 캡스톤 최소 구현 범위와 후속 범위

### 최소 구현

- 한 저장소의 고정 분석 스냅샷과 대상 파일 묶음 선택
- 파일별 수정 근거·표본 부족·수집 부족 표시
- 개인 작업 공간의 준비 체크폼 저장·수정·버전 관리
- 근거가 포함된 AI 점검 결과와 인수인계 초안 생성
- 일반 텍스트 편집·저장 및 Markdown 내보내기
- 작성자·저장소 권한 확인, 생성 실패·중복 요청 처리

### 후속 구현

- 팀 구성원·역할과 공동 편집·공유 권한
- 담당자별·폴더별 통합 현황 및 별도 집계 API
- 전체 팀 자동 진단과 여러 인계 대상 비교
- 개선 행동의 별도 진행 관리와 일정 제안
- 문서 링크 내용 연동과 실행 확인 도구
- 풍부한 문서 편집기 및 다른 문서 형식 내보내기

팀 공동 편집이 캡스톤의 필수 요구가 되면 팀·역할 모델을 최소 범위에 포함하고, 다른 후속 기능을 줄여 범위를 조정합니다.

## 12. 담당별 개발 범위와 순서

| 담당 | 개발 범위 |
|---|---|
| 데이터 수집 팀원 | 커밋·PR·리뷰 수집 완전성, 기여자 식별, 실패 사유와 누락 재수집, 근거 품질 제공 |
| 시각화 팀원 | 대상 선택, 근거·부족 상태 표시, 준비 체크폼, 점검·초안 표시, 편집·내보내기 화면 |
| 백엔드·분석 | 집계 정의, 권한·준비 정보 저장 및 버전, 근거 구성, AI 처리·검증·저장, 중복 요청·오류 관리 |

개발 순서는 다음과 같습니다.

1. 인계 대상·준비 정보·권한과 근거 데이터의 계약을 정합니다.
2. AI 없이 대상 선택, 준비 정보 저장, 근거 표시와 기본 문서 내보내기를 연결합니다.
3. 검증 가능한 형식으로 AI 점검·초안 생성을 연결합니다.
4. 부족한 근거, 실패·권한·변경 이력을 검증하고 사용자 시연을 진행합니다.

## 13. 검증 기준

| 검증 대상 | 통과 기준 |
|---|---|
| 수치·근거 일치 | 표시된 수치와 분모가 원본 근거와 일치하고 모든 참조가 실제 대상에 속함 |
| 준비 상태 | 미입력을 미확인으로 유지하고, 준비 필요·완료를 입력과 일치하게 설명함 |
| 표본·수집 부족 | 0건·5건 미만·미식별 기여자·PR 리뷰 누락 사례에서 정한 제한을 지킴 |
| 과도한 진단 | 준비 완료·근거 부족 사례에 없는 문제나 실제 업무량·지식 인원 판단을 추가하지 않음 |
| 문서 내용 | 제공되지 않은 코드 동작·실행 방법을 사실처럼 작성하지 않음 |
| 권한 | 다른 작성자·로그아웃·저장소 권한 상실의 조회·생성·편집·내보내기를 차단함 |
| 변경 이력 | 준비 변경·대상 변경·재생성·동시 편집에서 이전 결과와 편집본을 보존함 |
| 입력·출력 처리 | 악의적인 메모 지시, 잘못된 근거 참조·수치, 실행 가능한 출력을 처리함 |
| 실패 대응 | AI 오류·지연·중복 클릭에도 분석 조회와 기존 입력·편집본이 유지됨 |

수치 일치와 권한 차단처럼 자동으로 확인할 수 있는 항목은 테스트로 검증합니다. 설명의 사실성·이해도·유용성은 정해진 사례에 대한 사람의 검토로 평가합니다. 모델을 다시 호출할 때 표현이 달라질 수 있으므로 문장 일치 대신 근거·수치·금지된 판단의 준수 여부를 확인합니다.

사용 평가에서는 동일한 인계 과제로 기존 방식과 GitViz 사용 시 작성 시간, 누락된 필수 항목, 인수자의 실행 확인 결과를 비교합니다. 순서 효과를 줄이도록 과제와 사용 순서를 나누고 참여 인원·과제·조건을 함께 기록합니다. 소규모 평가 결과를 일반적인 생산성 향상으로 확대해 주장하지 않습니다.

## 14. 발표 구성

1. **문제:** 주요 담당자가 자리를 비우기 전에 인계할 파일과 준비할 정보를 찾기 어렵습니다.
2. **접근:** 개발 기록과 사용자가 확인한 준비 정보를 연결합니다.
3. **시연:** 파일 묶음 선택 → 수정 근거 확인 → 준비 입력 → AI 점검·초안 → 편집·내보내기.
4. **근거:** 수치의 단위·분모, 표본 부족, 수집 누락, 미확인 상태 처리를 설명합니다.
5. **검증:** 수치·권한·오류 검증과 사용자 평가 결과를 제시합니다.
6. **확장:** 팀 공동 편집과 여러 인계 대상 관리 계획을 소개합니다.

### 발표용 소개 문장

> “GitViz는 개발 기록에서 수정이 집중된 파일을 찾고, 사용자가 입력한 준비 상태와 연결해 인수인계에서 확인할 항목을 알려주는 AI 도우미입니다. 근거를 쉬운 말로 설명하고, 팀이 검토·보완할 인수인계 초안을 제안합니다.”
