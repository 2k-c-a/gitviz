# GitViz AI 활용 기획 v0.3

**PR 변경 설명부터 코드리뷰·인수인계·팀 점검까지**

- 작성일: 2026-10-07
- 버전: v0.3
- 기존 문서: [AI 도우미 기획 v0.2](GitViz_AI_도우미_기획_v0.2.md)
- 기존 기능 확인 기준: GitViz `0ecbca7`
- 문서 성격: 단계별 개발 기획. 아래 AI 기능은 구현 완료를 의미하지 않습니다.

## 1. 서비스 목표

GitViz가 수집·분석한 개발 이력과 PR의 변경 코드를 연결해, 사용자가 변경 내용을 이해하고 검토하며 다른 팀원에게 인계할 수 있도록 돕습니다.

핵심 흐름은 **변경 이해 → 코드 검토 → 과거 이력 확인 → 인수인계 준비 → 팀 단위 점검**입니다. AI는 설명과 검토 후보를 제안하고, 사용자는 근거를 확인하고 최종 판단합니다.

일반적인 코드리뷰에 GitViz의 수정 집중도·공동 변경·수집 품질 정보를 연결하는 것을 차별점으로 삼습니다. 과거 이력은 검토할 대상을 찾는 자료이며, 코드 오류나 사람의 역량을 확정하는 증거로 사용하지 않습니다.

## 2. 구현 우선순위

| 순위 | 기능 | 핵심 결과 | 선행 조건 |
|---|---|---|---|
| 1 | PR 변경 요약·설명 | 무엇이 어떻게 바뀌었는지 근거와 함께 설명 | PR 변경 코드 확보, 권한·AI 요청 기반 |
| 2 | 선택한 PR의 AI 코드리뷰 | 파일·줄 단위 문제 가능성과 확인 방법 | 1단계 입력·결과 저장 기반 |
| 3 | GitViz 분석과 리뷰 연결 | 함께 확인할 파일과 수정 집중 근거 | 2단계 + 기준이 명확한 분석 스냅샷 |
| 4 | 인수인계 초안 생성 | 변경 설명·검토 결과·준비 상태를 연결한 문서 | 1~3단계 결과 + 준비 정보 관리 |
| 5 | 전체 팀 진단·자동 리뷰 | 팀 점검 보고서와 새 변경의 자동 검토 | 2~3단계 검증, 팀 권한·이벤트 처리 기반 |

캡스톤의 첫 구현 목표는 **1~2단계의 수동 실행**입니다. 차별점을 보여주는 목표는 3단계까지이며, 4단계는 문서 활용으로 확장합니다. 5단계는 팀 점검과 자동 리뷰를 각각 독립적으로 도입합니다.

단계 순서는 우선순위입니다. 5단계 자동 리뷰는 인수인계 문서 없이도 구현할 수 있지만, 수동 리뷰의 품질과 비용을 확인한 후 도입합니다.

## 3. 공통 기반 — 모든 단계 전에 준비할 것

### 3.1 변경 코드와 기준 고정

사용자가 저장소와 PR을 선택하면 PR 번호, 제목·설명, 기본/대상 브랜치, 기준 커밋, 변경 커밋, 변경 파일과 diff를 확보합니다. 필요한 경우 선택한 커밋의 주변 함수·클래스 등 제한된 코드를 추가합니다.

PR 비교 기준은 merge-base와 head SHA를 기록하고 변경 내용을 고정합니다. 기본 브랜치가 바뀌거나 PR에 새 커밋이 추가돼도 기존 결과의 입력은 바뀌지 않습니다. 현재 PR과 저장된 결과의 SHA가 다르면 ‘이전 변경 기준’이라고 표시합니다.

페이지 누락, 잘린 diff, 읽을 수 없는 파일은 입력 상태로 기록합니다. 대형 변경, 바이너리, 생성 파일 등은 제외 사유를 표시하며, 읽지 않은 파일을 검토한 것처럼 표시하지 않습니다. PR 파일 목록을 확보한 것과 코드 본문을 확보한 것을 별도로 기록합니다.

### 3.2 권한과 코드 전송

첫 버전의 결과는 로그인한 작성자의 개인 작업 공간에 저장합니다. 생성·조회·내보내기 때 작성자 권한과 현재 GitHub 저장소 접근 권한을 확인합니다. 공개 저장소를 읽을 수 있다고 다른 사람의 메모·문서에 접근할 수는 없습니다.

v0.2의 ‘코드 원문을 전달하지 않음’ 정책을 확장합니다. **코드리뷰 실행 시 선택한 PR의 diff와 필요한 주변 코드를 외부 AI에 전달할 수 있습니다.** 인수인계 생성에는 검증된 설명·근거를 우선 재사용하고, 원문이 필요하면 별도로 전달 범위에 포함합니다.

실행 전 제공자, 대상 PR, 전송할 파일과 코드 범위를 보여줍니다. 비공개 저장소는 팀에서 외부 AI 사용을 허용한 저장소에 한정합니다. 허용 기준을 정하기 전에는 공개 저장소로 시연합니다. API 키는 서버에서 보관합니다.

저장소 전체를 기본 전송 대상으로 삼지 않습니다. 코드·주석·PR 설명·메모는 분석 자료이며 모델의 행동을 바꾸는 명령으로 사용하지 않습니다. 비밀 값이 의심되는 자료는 자동 전송하지 않고 제외·검토 대상으로 처리하되, 자동 탐지가 모든 비밀을 찾아낸다고 보장하지 않습니다.

### 3.3 요청·비용·결과 관리

입력 파일 수·코드 크기·요청 시간·동시 실행·사용자별 요청량의 한도를 서버에서 설정합니다. 범위를 넘으면 사용자가 대상을 줄이도록 안내하거나 파일 단위로 나누되, 각 결과가 다룬 범위를 표시합니다.

상태는 대기·진행·완료·실패·취소로 관리하고, 결과에 입력 범위와 누락 상태를 별도로 표시합니다. 동일 입력·기능·모델·프롬프트 버전은 진행 중 요청이나 기존 결과를 재사용합니다. 실패 요청은 제한된 횟수만 재시도하며 분석 조회는 계속 사용할 수 있게 합니다.

결과에는 저장소, PR, 기준 SHA, 입력 해시, 모델·프롬프트 버전, 생성 시점, 사용량·처리 시간과 검증 상태를 기록합니다. 과거 결과는 보존하고 재생성으로 사용자 편집 내용을 덮어쓰지 않습니다.

출력은 정해진 구조로 받고 파일·줄·근거 참조를 검증합니다. Markdown/HTML 표시 시 실행 가능한 내용을 차단합니다. 코드와 메모 원문을 운영 로그에 불필요하게 남기지 않습니다. 저장된 결과·입력의 보관 기간과 삭제 정책은 도입 전에 정합니다.

## 4. 1단계 — PR 변경 요약·설명

### 목적과 사용자 흐름

리뷰어와 인수자가 변경의 핵심을 빠르게 파악하도록 돕습니다.

**저장소 선택 → PR 선택 → 전송 범위 확인 → 변경 설명 생성 → 파일별 근거 확인**

### 입력과 결과

| 구분 | 내용 |
|---|---|
| 입력 | 고정된 PR 정보, 파일 목록, diff, 필요한 주변 코드, 입력 누락 상태 |
| 결과 | 변경 요약, 파일별 주요 변경, 이전/이후 동작 설명, 검토할 질문, 제외·미확인 범위 |
| 근거 표시 | 파일 경로, 코드 위치, 기준 SHA, diff 또는 제공된 코드 참조 |

PR 설명에 적힌 의도는 작성자의 설명으로 구분합니다. 코드에서 확인한 변경과 동일한 사실로 취급하지 않습니다. 실행하지 않은 결과, 제공되지 않은 호출 관계나 서비스 전체 동작은 확정하지 않습니다.

**가상의 출력 예시**

> `auth/session.py`에서 만료된 세션을 처리하는 분기가 추가됐습니다. 변경된 분기는 오류 응답을 반환합니다. 호출자가 해당 응답을 처리하는지는 제공된 범위에서 확인하지 못했습니다.

### 첫 구현 범위와 완료 기준

PR 하나를 사용자가 수동으로 선택해 실행합니다. 요약과 파일별 설명을 저장하고 기존 결과를 다시 조회할 수 있게 합니다.

주요 변경을 빠뜨리지 않고 설명의 파일·코드 참조가 실제 입력과 일치해야 합니다. 변경하지 않은 동작이나 실행 성공을 만들어내지 않아야 합니다. 누락된 코드가 있으면 그 범위를 표시해야 합니다.

## 5. 2단계 — 선택한 PR의 AI 코드리뷰

### 목적과 사용자 흐름

변경 코드의 오류 가능성과 확인할 테스트를 제안합니다.

**변경 설명 확인 → 코드리뷰 실행 → 지적별 코드·근거 확인 → 유효 여부 기록**

### 리뷰 범위와 출력

우선 검토 대상은 조건 분기·경계값, 예외·빈 값 처리, 자원·상태 처리, 접근 권한 확인, 변경된 동작의 테스트 누락입니다. 언어별 지원 범위는 검증한 언어부터 명시적으로 늘립니다.

| 항목 | 표시할 내용 |
|---|---|
| 위치 | 파일, 이전/이후 코드 구분, 줄 또는 줄 범위 |
| 문제 가능성 | 어떤 조건에서 문제가 발생할 수 있는지 |
| 중요도 | 영향과 근거에 따른 검토 순서. 확정된 장애 등급으로 표현하지 않음 |
| 근거 | 해당 코드와 추론, 확인하지 못한 전제 |
| 확인 방법 | 재현할 입력·상황 또는 추가할 테스트 |
| 개선 방향 | 수정 제안. 자동 적용하지 않음 |

**가상의 출력 예시**

> 빈 목록이 들어오면 첫 항목에 접근하는 부분에서 예외가 발생할 수 있습니다. 빈 입력을 처리하는 상위 호출자가 있는지는 확인하지 못했습니다. 빈 목록 테스트로 실제 동작을 확인해 보세요.

검토 결과와 사람의 피드백은 유효·오탐·판단 보류로 구분해 저장하고 사유를 남깁니다. 지적이 0개여도 ‘오류 없음’이나 ‘안전함’으로 표시하지 않습니다. 테스트를 실행하지 않았다면 실행하지 않았음을 표시합니다.

### 첫 구현 범위와 완료 기준

수동 리뷰 결과를 GitViz 안에서 확인합니다. 코드 자동 수정, PR 승인·병합, GitHub 댓글 등록은 포함하지 않습니다.

알려진 결함이 있는 변경과 정상 변경을 함께 검증합니다. 유효 지적 비율, 알려진 결함 발견 비율, 오탐 수, 코드 위치 정확도를 기록합니다. 발견하지 못한 결함도 남기며 모델별 성능 수치를 검증 전에 약속하지 않습니다.

## 6. 3단계 — GitViz 분석과 리뷰 연결

### 목적과 사용자 흐름

변경 코드만으로 보이지 않는 과거 수정 이력을 검토 대상으로 연결합니다.

**리뷰 결과 확인 → 연결할 분석 스냅샷 선택 → 이력 기반 확인 대상 조회 → 코드 지적과 구분해 검토**

| 분석 근거 | 제공할 도움 | 표현 제한 |
|---|---|---|
| 과거 공동 변경 | 이번 변경과 함께 확인할 파일 후보 | 이번에 수정하지 않았다고 오류로 확정하지 않음 |
| 파일별 기여 비중 | 기존 담당자에게 물어볼 질문 | 실제 업무량·능력·지식 인원으로 해석하지 않음 |
| 관측 수·미식별 비중 | 설명의 근거 부족 안내 | 식별된 비중을 전체 변경 비중으로 표현하지 않음 |
| PR·리뷰 수집 상태 | 사용할 수 있는 협업 근거 구분 | 누락을 리뷰 부재로 해석하지 않음 |
| 상대 점검 우선순위 | 검토 후보의 순서 참고 | 장애 확률로 해석하지 않음 |

**가상의 출력 예시**

> 선택한 과거 분석에서 `session.py`와 `token.py`는 함께 변경된 기록이 있습니다. 이번 PR에서 `token.py`는 변경되지 않았습니다. 이번 변경과 관련이 있는지 확인해 보세요. 이 기록만으로 수정 누락을 의미하지는 않습니다.

### 기준과 완료 조건

코드리뷰는 PR의 비교 SHA를 기준으로 하고, 과거 이력은 선택한 스냅샷의 SHA·관측 기간을 기준으로 합니다. 두 기준이 다르면 함께 표시합니다. 열린 PR의 코드 상태와 과거 기본 브랜치 분석을 같은 시점의 자료처럼 합치지 않습니다.

분석에 없는 새 파일은 이력 없음으로 표시합니다. 이름 변경을 자동으로 동일 파일로 추정하지 않습니다. 관측 수 5 미만은 현행 분석 정책에 따라 표본 부족으로 표시합니다. 파일별 건수를 단순 합산해 폴더 전체의 고유 커밋 수로 표현하지 않습니다.

파일 대응·근거 수치·스냅샷 참조가 일치해야 합니다. 이력 자료가 없어도 1~2단계는 동작해야 하며, 코드 지적과 이력 기반 확인 후보를 화면에서 구분해야 합니다.

## 7. 4단계 — 인수인계 초안 생성

### 목적과 사용자 흐름

검토한 변경을 다른 팀원이 이해하고 이어서 확인할 수 있는 문서로 정리합니다.

**PR·분석 결과 선택 → 인계 대상 설정 → 준비 정보 입력 → 초안 생성 → 편집·저장 → Markdown 내보내기**

v0.2의 준비 정보 관리 원칙을 유지합니다. 인계 대상 파일 묶음별로 인수 담당자, 기능 설명, 실행 방법, 수정 후 확인 절차, 공동 검토, 인수자 실행 확인을 미확인·준비 필요·준비 완료로 저장합니다. 작성자·수정 시점·버전을 기록합니다.

### 문서 구성

1. 인계 목적과 대상 파일·담당자 메모
2. 이번 PR의 주요 변경과 코드 근거
3. AI 리뷰에서 제안한 확인 항목과 사람의 검토 상태
4. 과거 이력에서 함께 확인할 파일
5. 입력된 준비 상태와 미확인 항목
6. 담당자에게 물어볼 질문과 체크리스트
7. PR 기준 SHA, 분석 기간, 준비 정보 버전과 생성 시점

검증되지 않은 AI 리뷰 지적은 확정된 결함으로 문서에 넣지 않습니다. 실행 절차·환경 정보가 제공되지 않았다면 확인 질문과 작성 항목으로 남깁니다. ‘준비 완료’는 사용자 기록이며 자동 검증된 실행 성공이 아닙니다.

### 첫 구현 범위와 완료 기준

일반 텍스트 편집·저장과 Markdown 내보내기를 제공합니다. 생성 원본과 편집본을 분리합니다. 준비 정보·대상 파일·PR이 변경되면 이전 기준의 문서임을 표시하고 재생성으로 편집본을 덮어쓰지 않습니다. 동시 수정은 버전 확인으로 충돌을 처리합니다.

초안이 실제 선택한 결과·준비 정보와 일치하고 미확인을 준비 부족으로 바꾸지 않아야 합니다. 누락 항목과 작성 시간은 동일한 인계 과제로 사용자 평가하며 소규모 평가 조건을 함께 기록합니다.

## 8. 5단계 — 전체 팀 진단·자동 리뷰

### 8.1 팀 점검 보고서

팀이 허용한 저장소·기간·인계 대상을 선택해 수정 집중 현황, 준비 필요·미확인 항목과 반복된 유효 리뷰 지적을 요약합니다. 근거 파일·PR·기간으로 이동할 수 있게 합니다.

개인 점수나 순위를 만들지 않습니다. 변경 건수, 리뷰 건수, AI 지적 수를 성과·능력으로 해석하지 않습니다. 오탐·미검토 지적은 확인된 문제 수에 포함하지 않으며, 여러 커밋에 걸친 동일 지적은 중복으로 집계하지 않습니다.

팀 보고서는 팀 구성원·관리자·역할 및 공유 권한을 마련한 뒤 제공합니다. 각 원본 저장소와 문서의 접근 권한을 확인하고, 사용자가 볼 수 없는 자료를 요약에 노출하지 않습니다. 개인 메모는 명시적인 팀 공유 범위에 포함된 경우에만 사용합니다.

### 8.2 자동 PR 리뷰

저장소 관리자가 자동 리뷰를 켠 저장소에 한해 PR 생성·갱신 이벤트를 받아 검토합니다. 첫 자동화는 결과를 GitViz에 저장하고, GitHub 댓글은 별도 설정을 켠 경우에만 게시합니다. 자동 승인·병합·코드 변경은 범위에 포함하지 않습니다.

이벤트 서명을 검증하고 저장소 ID·설정·권한을 확인합니다. 전달 이벤트 ID로 중복 수신을 제어하고, 실제 생성 작업은 고정된 비교 SHA·입력·기능 버전으로 중복 실행을 막습니다. 저장소별 동시 실행·사용량 한도와 대기열을 관리합니다.

새 커밋으로 이전 작업이 오래된 경우 취소하거나 이전 기준으로 표시합니다. 댓글 게시 직전에 현재 SHA와 게시 권한을 확인해 오래된 지적이 최신 코드의 줄에 붙지 않게 합니다. 실패·재시도·사용량을 확인하고 저장소별로 자동화를 끌 수 있게 합니다.

### 완료 조건

팀 보고서에서 권한 밖 자료가 노출되지 않아야 합니다. 중복·역순 이벤트, 새 커밋, 권한 상실, 한도 초과, AI 오류에서도 중복 실행·중복 게시·오래된 줄 연결을 방지해야 합니다. 수동 리뷰에서 검증한 품질 기준을 유지하고 비용·오탐을 점검한 뒤 적용 범위를 늘립니다.

| 시각화 팀원 | PR 선택·코드 위치 표시, 설명·리뷰·이력 근거 화면, 체크폼·편집·내보내기, 팀 보고서·설정 화면 |
| 백엔드·분석 | 권한·데이터 계약, 근거 연결·집계, AI 작업·검증·저장, 준비 정보 버전, 비용·오류·이벤트 처리 |

개발 시작 전에 입력·출력 계약을 함께 정합니다. 특히 파일 경로, 이전/이후 줄 위치, SHA, 코드 확보 상태와 분석 스냅샷 ID를 공통 식별자로 사용합니다. 이 문서는 작업 분담 기획이며 팀원이 맡은 수집·시각화 코드를 변경하지 않습니다.

## 11. 구현 순서와 단계 통과 기준

| 순서 | 만들 것 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 기반 | 권한, 고정 입력, 수집 품질, AI 작업·결과 저장 | 같은 입력 식별 가능, 권한 차단·실패·중복 처리 확인 |
| 1 | 수동 PR 변경 설명 | 원본과 설명 일치, 코드 근거·누락 표시 확인 |
| 2 | 수동 코드리뷰·사람의 피드백 | 결함·정상 사례에서 발견과 오탐 기록, 위치 검증 |
| 3 | 이력 연결 | 기준 차이·근거 부족 표시, 코드 지적과 이력 후보 구분 |
| 4 | 준비 체크폼·초안·내보내기 | 입력 상태 일치, 편집본 보존, 권한·버전 검증 |
| 5 | 팀 보고서·자동 실행 | 공유 권한·이벤트·사용량·게시 안정성 확인 |

인력·기간이 부족하면 1~3단계를 우선 완성하고 4~5단계는 후속 계획으로 제시합니다. 다섯 기능을 동시에 얕게 구현하기보다 각 단계가 실제 입력부터 결과 조회까지 이어지도록 완성합니다.

## 12. 검증 계획

고정된 PR 비교 SHA와 정답 검토 자료를 가진 사례 묶음을 사용합니다. 결함 삽입 사례와 정상 변경, 빈 값·경계값·권한 처리, 테스트 누락, 대형·잘린 diff를 포함합니다. 실제 PR은 사람이 먼저 검토해 결함·질문·오탐 판단의 기준을 기록합니다.

| 항목 | 확인할 내용 |
|---|---|
| 설명 정확성 | 제공된 변경과 설명의 일치, 주요 변경 누락, 근거 없는 주장 |
| 리뷰 품질 | 유효 지적 비율, 알려진 결함 발견 비율, 오탐·판단 보류 수 |
| 위치·수치 | 실제 파일·줄·SHA·근거 참조와 수치 일치 |
| 근거 부족 | 입력 누락·표본 부족·미식별·이력 없음 처리 |
| 입력 공격 | 코드 주석·PR 설명의 지시가 추가 전송·행동을 유발하지 않음 |
| 권한·정보 노출 | 다른 작성자·팀·저장소 자료 차단, 외부 전송 범위 준수 |
| 실패·변경 | AI 실패, 중복 클릭, 새 커밋, 편집 충돌, 이벤트 중복 처리 |
| 비용·시간 | 요청당 사용량·처리 시간, 한도·취소·재사용 동작 |
| 사용자 가치 | 변경 이해 시간, 유효한 확인 항목, 문서 누락과 작성 시간 |

사례 수·언어·변경 규모와 평가 조건을 공개합니다. 프롬프트 조정용 사례와 최종 평가 사례를 나누고, 같은 사례를 반복해 맞춘 결과를 일반적인 정확도로 제시하지 않습니다. AI 결과의 표현이 달라도 근거와 의미를 기준으로 평가합니다.

## 13. 발표 흐름

**PR 선택 → 변경 설명 → 줄 단위 리뷰 → 과거 공동 변경 근거 → 준비 정보 입력 → 인수인계 초안**을 시연합니다. 팀 점검·자동 리뷰가 구현되지 않았다면 확장 계획으로 구분합니다.

발표에서는 ‘AI가 오류를 보장해서 찾아준다’보다 ‘변경을 설명하고 검토 근거와 확인 방법을 제안한다’고 소개합니다. 코드리뷰 지적, 이력 기반 확인 후보, 사용자 입력 상태의 차이를 실제 화면에서 보여줍니다.

> “GitViz는 PR의 변경 내용을 설명하고 코드 검토를 돕는 AI 도우미입니다. 과거 수정 이력과 준비 정보를 연결해, 팀원이 확인할 파일과 질문을 찾고 인수인계 문서로 이어갈 수 있게 합니다.”

## 14. v0.2 대비 변경 사항

| 항목 | v0.2 | v0.3 |
|---|---|---|
| 시작점 | 인계 대상 파일 묶음 | PR 변경 설명과 코드리뷰 |
| 개발 순서 | 준비 점검·초안 중심 | 설명 → 리뷰 → 분석 연결 → 초안 → 팀·자동화 |
| AI 입력 | 분석 수치·준비 정보 중심, 코드 원문 제외 | 선택한 diff·필요한 주변 코드 전송 가능, 범위 안내 |
| 근거 식별 | 분석 스냅샷·준비 버전 | PR 비교 SHA·코드 위치·분석 스냅샷·준비 버전 |
| 차별점 | 수정 집중과 준비 상태 연결 | 코드리뷰에 과거 이력을 연결하고 인수인계로 확장 |
| 검증 | 점검·문서·권한 | 결함 발견·오탐·코드 위치·이벤트·비용 검증 추가 |

v0.2의 미확인 처리, 준비 정보 버전, 작성자 권한, 생성 원본·편집본 분리 원칙은 유지합니다. 현재 코드에서 확보한 PR 상세·분석 스냅샷은 활용 기반이며, 코드 본문 수집·AI 기능·팀 권한·자동 리뷰는 추가 개발 대상입니다.
