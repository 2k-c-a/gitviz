## 확인한 문제

### P1 — 멈춘 분석을 재시작할 수 없다

위치: `app/api/repositories.py:254`, `frontend/js/modal.js:246`.

`_trigger_analysis()`는 pending/running/rate_limited 작업이 하나라도 있으면 무조건 409를 반환한다. 프론트의 멈춤 안내는 같은 URL로 POST해서 재시작하려 하지만, 기존 작업의 상태를 종료하지 않으므로 똑같이 409가 난다. 워커가 죽고 running이 남으면 사용자에게 안내한 복구 경로가 동작하지 않는다.

또한 `_compute_staleness()`는 pending을 검사하지 않는다. 실제 함수를 분리 실행해 이틀 전 생성된 pending 작업도 `is_stale=False`임을 확인했다. 큐 등록 후 워커가 실행하지 못하면 대기 상태가 계속 남고 신규 요청도 막힌다.

개선: 작업 heartbeat와 소유권/lease를 기록하고, 저장소 잠금 아래에서 만료 작업을 종료한 후 새 작업을 만든다. 장시간 계산 중인 정상 작업을 단순 시간 초과만으로 중복 실행하지 않도록 한다. pending에도 큐 대기 만료/복구 정책을 적용한다.

### P1 — 문서의 설치 절차로 빈 DB를 준비할 수 없다

위치: `migrations/versions/393e33b2dcbb_create_files_table.py:24`, `migrations/versions/b5c6d7e8f9a0_add_github_api_tables.py:20`, `migrations/versions/e2f3a4b5c6d7_repository_access_snapshots.py:25`.

Alembic 이력에 repositories/contributors/analysis_jobs의 생성이 없는데 이후 migration은 해당 테이블을 참조한다. 오늘 migration은 `analysis_jobs.triggered_by_user_id`를 사용하지만 이 컬럼 추가는 별도 수동 스크립트에만 있다. `commits.on_default_branch` 역시 Alembic에 없다. 기존 DB가 수동 스크립트로 준비돼 있으면 통과할 수 있지만 새 DB/부분 적용 DB에서는 실패한다.

`app.main`의 create_all도 기존 테이블에 누락 컬럼을 추가하지 않으며 migration 순서와 충돌할 수 있다.

개선: 과거 수동 변경을 정식 migration에 편입하고 빈 PostgreSQL에 설치 → 서버 시작 → 작은 저장소 수집까지 CI에서 확인한다. 배포 시 migration을 명시적으로 실행하고 앱 import의 DDL은 제거한다. 이 항목은 코드 이력 검토 결과이며 실제 빈 PostgreSQL 적용은 이번에 실행하지 않았다.

### P2 — 권한/한도 오류가 나면 분석 모달이 계속 기다린다

위치: `frontend/js/modal.js:163`, `app/api/repositories.py:433`, `app/services/repository_access.py:83`.

상태 조회는 매번 GitHub 권한 검사를 한다. 프론트는 2초마다 조회하고 401/404/429/502를 포함한 모든 비정상 응답을 `if (!res.ok) return`으로 무시한다. 로그인 만료, 권한 회수, GitHub 제한이 발생하면 설명 없이 같은 화면에서 계속 요청한다. 폴링만 탭당 시간당 약 1,800회이며 수집 API 요청과 별도로 발생한다. ETag도 현재 코드는 HTTP 요청 자체를 보내므로 외부 왕복은 계속된다.

개선: 401은 재로그인 안내, 404는 접근 불가 안내, 429는 재시도 시각과 backoff, 502는 제한된 재시도를 적용한다. 요청이 진행 중일 때 다음 폴링을 겹치지 않게 한다. 권한 확인을 생략하는 캐시로 해결하면 권한 회수 반영이 약해지므로 별도의 보안 요구사항으로 설계해야 한다.

### P2 — 과거 결과 링크가 페이지 이동 중 바뀔 수 있다

위치: `frontend/js/navbar-loader.js:27`, `frontend/js/api.js:43`.

`goPage()`는 repo만 전달하고 URL의 snapshot은 버린다. 목적지는 sessionStorage의 snapshot에 의존한다. 같은 탭에서 같은 저장소의 다른 결과를 먼저 열면 저장값이 덮어써지므로 과거 결과 페이지로 돌아온 뒤 분석 탭을 전환할 때 다른 스냅샷이 선택될 수 있다.

개선: 현재 repo가 같으면 URL의 snapshot을 함께 전달하고, 새 분석 결과 보기에는 완료 job의 snapshot ID를 명시한다. 서로 다른 repo에는 이전 snapshot을 전달하지 않는다. 페이지 이동과 과거 결과 재열기 회귀 검사가 필요하다.

## 발전 우선순위

1. **운영 안정화:** 위 P1 문제, 오류별 프론트 복구, 빈 DB 설치 CI, 로그인/비공개 저장소/재분석 E2E를 먼저 해결한다. 수집 실패율·작업 heartbeat·큐 대기·GitHub 잔여 한도를 관찰한다.
2. **분석 근거와 검증:** 점수마다 관측 건수와 수집 범위를 보여주고, 특정 기간의 결과가 이후 버그 수정/변경과 어떤 관계가 있는지 평가한다. 시간 순서로 학습·평가 구간을 분리하고 변경 빈도/churn 같은 단순 기준과 비교한다. 현재 상대 점수를 결함 확률로 표현하지 않는다.
3. **결과 비교:** 기존 불변 스냅샷을 활용해 두 SHA/기간의 파일 위험도, BF, 결합도 차이를 보여준다. 삭제·이동 파일 대응 규칙과 계산 버전 차이를 표시한다. '어느 파일을 먼저 살펴볼까'에 답하도록 근거 커밋/PR로 이어지는 우선 점검 목록을 만든다.
4. **대형 저장소 성능:** 스냅샷 한 JSON에 전체 네트워크·파일 정보를 담고 매 조회에 해시 검증/복사를 하는 비용을 측정한다. 결과 종류별 저장과 페이지 단위 조회, 네트워크 표본화/중심성 근사, 트리 점진 렌더링을 검토한다. 실제 측정 후 병목부터 최적화한다.
5. **제품 사용성:** ISO 시간과 계산 버전이 길게 나열된 안내를 '분석 기준·수집 범위·데이터 부족' 중심으로 요약하고 상세에서 기술 정보를 펼치게 한다. 최신 결과와 과거 결과를 구분하고 재분석 실패 중에도 마지막 성공 결과에 접근할 수 있게 한다.

가장 가치가 높은 다음 단계는 **설치/복구 안정화 → 분석 근거 검증 → 스냅샷 비교 기능**이다.
