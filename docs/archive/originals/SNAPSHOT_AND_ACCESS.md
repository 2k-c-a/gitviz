# 저장소 격리와 분석 결과 저장

## 구현

- 수집 경로는 `storage/repos/<repository_id>`다. 동명 저장소는 별도 디렉토리를 사용하고 기존 클론의 origin이 다르면 갱신하지 않는다. Git 인증은 자식 프로세스 환경에만 전달하고 URL이나 `.git/config`에 토큰을 저장하지 않는다. 저장소별 advisory lock으로 동시 수집을 막는다.
- URL은 HTTPS GitHub의 소유자/저장소 두 경로만 허용한다. GitHub의 숫자 ID와 공개 여부를 저장한다. 확인되지 않은 공개 여부는 공개 목록에 노출하지 않는다.
- GitHub 숫자 ID가 없는 이전 저장소는 주소만으로 과거 결과와 현재 저장소를 동일하다고 가정하지 않는다. 해당 URL을 새로 등록하면 새 ID/수집 경로로 분석한다. 주소가 삭제 후 재사용돼도 이전 저장소의 결과를 노출하거나 새 저장소에 합치지 않는다.
- 분석 요청에는 로그인이 필요하다. private 저장소의 조회·수집은 요청자의 개인 토큰으로 현재 GitHub 접근 권한을 확인한다. 서버 공용 토큰이나 과거 분석 참여 기록만으로 private 접근을 허용하지 않는다. 목록/상태/상세/분석 조회도 같은 권한 검사를 적용한다.
- GitHub가 인증과 최신 상태를 확인한 HTTP 304 응답에만 ETag 캐시를 재사용한다. GitHub 장애나 API 제한 시 권한 확인을 생략하지 않는다. 공용 토큰 제한에 한해서 비인증 공개 조회로 확인할 수 있지만 private는 열리지 않는다.
- 운영 세션에 기본 비밀키를 허용하지 않는다. HTTPS 배포에서는 `SESSION_COOKIE_SECURE=1`을 설정한다.
- 분석 요청마다 새 작업을 생성한다. 진행 중인 작업이 있으면 409로 알려 요청 기간이 조용히 무시되지 않게 한다. 완료 시 결과 저장과 작업 완료를 같은 트랜잭션으로 확정한다.
- 결과에 기준 SHA, 분석 구간 `[start,end)`, 계산 버전, 실행 시각, 파라미터, JSON 결과와 SHA-256을 저장한다. 숫자 표현은 JSONB 저장 전후에 같도록 정규화한다. DB 트리거가 기존 스냅샷의 UPDATE/DELETE를 차단한다. 무결성이 맞지 않는 결과는 반환하지 않는다.
- 조회 API는 저장된 결과를 선택/필터링한다. 프론트는 스냅샷 ID를 고정하고 URL의 `repo`와 `snapshot`으로 다시 열 수 있다. GitHub 코드 링크도 브랜치 대신 기준 SHA를 사용한다.
- 결합도에 각 파일 변경 건수, 양방향 비율, 공동 변경 건수를 포함한다. PR 파일 기록이 없는 경우 커밋으로 대체한다. 공동 변경 2건 이상인 쌍만 반환한다. 5건 미만 표시는 UI 정책이며 통계적 신뢰수준이 아니다.
- 이력 없음/관측 부족, 작성자 미식별, 계정 미연결, PR 커밋 연결, 기준 SHA 파일 수집 수를 표시한다. 수집된 데이터에서의 비율이며 전체 GitHub 데이터 수집 완료를 뜻하지 않는다.

## 기간 지정과 추후 검증

`POST /repositories` 또는 `POST /repositories/{id}/reanalyze`의 쿼리 파라미터:

```text
analysis_start=2024-10-02T00:00:00+09:00
analysis_end=2026-07-02T00:00:00+09:00
```

2026-10-02를 평가 기준일로 선택할 경우의 예시다. URL에는 `+`를 `%2B`로 인코딩한다. 시작 포함·종료 제외이고 시간대가 필요하다. 커밋/병합 PR/리뷰/릴리스는 종료 이후 데이터를 제외하고, 파일 트리는 종료 이전 커밋의 SHA에서 읽는다. 기본값은 시작 제한 없이 요청 시각 이전까지다.

**타당성 검증은 이번 작업에서 실행하지 않았다.** 이후 2년 전~3개월 전 데이터를 분석하고 최근 3개월 데이터를 검증에 사용하는 계획이다. 평가일·파일 대응 규칙·정답 정의·베이스라인은 그때 고정한다. 삭제/이동 파일과 미수집 이력의 처리도 정해야 한다. 현재 Git 그래프만으로 과거의 강제 push 전 브랜치 상태를 복원할 수는 없고, 과거 시점의 기여자 신원 매핑이 없으면 현재 신원 보정이 사용된다. 저장 결과 재조회와 엄밀한 과거 시점 데이터 복원은 별개의 요구사항이다.

## 운영 적용 및 검사

```text
python -m alembic upgrade head
python scripts/backfill_analysis_snapshots.py --apply
python scripts/test_analytics_calculations.py
python scripts/test_repository_snapshots.py
node scripts/test_metric_display.cjs
python scripts/verify_snapshot_integration.py
```

기존 이름 기반 클론은 origin을 검증한 뒤 읽기만 한다. 주소가 다른 클론은 저장하지 않고 `verified_clone_required`로 보고한다. `--offline-existing-data`는 외부 GitHub 확인 없이 기존 DB/클론만 읽는 유지보수 옵션이다. 공개 여부/사용자 권한은 갱신하지 않으며 HTTP 조회의 현재 GitHub 검사는 유지된다. `--repair-hashes`는 이전 결과를 보존하면서 새 해시 형식의 스냅샷을 추가한다.

`verify_snapshot_integration.py --auth-fixture`는 실제 운영 DB를 읽기 전용으로 사용하되 GitHub 인증을 테스트 대역으로 분리한다. 이 결과를 실제 GitHub 권한 검증 통과로 해석하면 안 된다. 일반 모드에서는 실제 GitHub 검사를 실행한다.

2026-10-02 적용: 마이그레이션 `e2f3a4b5c6d7`, 9개 기존 저장소 결과 저장, 최신 결과 해시 및 응답 계약 53개 검사 통과(인증 대역 모드). 접근 제어/저장 테스트 14개, 계산 테스트 9개와 프론트 회귀 검사 통과. 실제 브라우저에서 SHA 링크·스냅샷 정보·데이터 부족 표시·양방향 결합 비율을 확인했다. 최종 실제 GitHub 연동 재검사는 비인증 API 한도 때문에 완료하지 못했다. 타당성 검증은 실행하지 않았다.

로그인 가능한 일반 개발 서버는 `python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`이다. 읽기 전용 검증 서버는 OAuth 경로를 의도적으로 차단하므로 실제 로그인에 사용하지 않는다.
